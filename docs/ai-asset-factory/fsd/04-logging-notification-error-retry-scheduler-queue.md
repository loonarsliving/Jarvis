# FSD §20–25: Logging, Notification, Error Handling, Retry, Scheduler, Mission Queue Workflows

## 20. Logging Workflow

Every state-changing action in the system — human or system-actor — writes an immutable audit log entry. This is a hard requirement (NFR-3), not optional instrumentation.

### Log Entry Structure
`log_id`, `actor_type` (`human`/`system`), `actor_id`, `action` (dot-notation: `mission.created`, `asset.approved`, `dna.version_approved`, `job.retried`, `qc.lock_override`), `entity_type`, `entity_id`, `before_state` (jsonb, nullable), `after_state` (jsonb), `metadata` (jsonb — free-form context, e.g. override justification text), `timestamp`, `severity` (`info`/`warning`/`critical`).

### What Gets Logged
- Every Mission lifecycle transition.
- Every Generation Job status transition (including every retry attempt with its specific error).
- Every DNA record creation/version approval/rejection.
- Every Prompt Template edit/promotion/rollback.
- Every QC decision (automatic and human).
- Every Drive operation (folder create, file upload, file move, reconciliation flags).
- Every permission-denied attempt (security-relevant, `severity=warning`).
- Every `qc.lock_override` (always `severity=critical`).

### Page: System Logs (`/settings/logs`, Super Admin only)
- **Purpose**: Full audit trail browsing for investigation/compliance.
- **UI Layout**: Filterable table (actor, action, entity type, date range, severity) with expandable row showing before/after diff.
- **Buttons**: `Filter`, `Export CSV` (Super Admin only, logged itself as `logs.exported` — exporting audit logs is itself an auditable action).
- **Permissions**: `user.manage` or dedicated `logs.view` (Super Admin only in v1).
- **Database Tables**: `audit_logs` (append-only, no update/delete API exposed at the application layer; retention policy set at the database/infrastructure level, not user-configurable in the UI).

## 21. Notification Workflow

### Channels
- **In-app** (bell icon, top bar) — always on, cannot be disabled per-user for `critical` severity events.
- **Email** — configurable per user per event category.
- **WhatsApp bridge** (optional, reusing the pattern already proven in MK Connect's WhatsApp integration, Master Planning `01-research-mkconnect.md` §6) — for `critical` events only (e.g., Mission auto-paused due to systemic Higgsfield failure), Super Admin only, opt-in.

### Event → Notification Matrix

| Event | Default channel(s) | Recipient(s) |
|---|---|---|
| Mission completed | In-app | Mission creator |
| Mission completed_with_failures | In-app + Email | Mission creator, Production Manager |
| Mission auto-paused (systemic failure) | In-app + Email + WhatsApp (if enabled) | Super Admin |
| Assets flagged for review (batch, hourly digest not per-asset to avoid spam) | In-app | QC Reviewers |
| DNA version awaiting approval | In-app | Creative Director |
| Repeated rejection pattern detected (§18) | In-app | Creative Director |
| `qc.lock_override` used | In-app + Email | All Super Admins |
| Google Drive quota >85% | In-app + Email | Super Admin |
| Dead-letter job count > threshold | In-app | Super Admin, Production Manager |

### Page: Notification Center (`/notifications`, also bell dropdown)
- **Components**: list, unread/read state, filter by category, `Tandai Semua Dibaca` button, click-through to relevant entity (Mission/Asset/DNA record).
- **System Actions**: notifications generated by the relevant service at the moment of the triggering event (not polled/batched, except the explicitly-noted hourly digest for review-flags).

## 22. Error Handling Workflow

### Principles
- No silent failure: every error is either recovered automatically (retry) or surfaced (notification + log), never both-absent.
- User-facing errors are translated to plain-language Bahasa Indonesia messages; technical detail (stack trace, provider error code) is preserved in the log entry, not shown raw to end users, but visible to Super Admin via drill-down.
- A failure in one Mission's jobs never blocks or corrupts another Mission's jobs (isolation).

### Error Categories & Standard Handling

| Category | Example | Handling |
|---|---|---|
| Transient infrastructure | Network timeout, temporary Higgsfield 5xx | Auto-retry per backoff policy (§24) |
| Provider content rejection | Higgsfield content-policy block | No auto-retry; flagged `failed_content_policy`, human decides |
| Provider quota/rate-limit | Higgsfield 429 | Auto-retry with extended backoff; Mission auto-pause if persistent |
| Data integrity | Checksum mismatch after download | Job marked `failed_integrity`, single auto-retry, then dead-letter if it recurs |
| Storage | Drive upload failure | Auto-retry per backoff; Reconciliation Job catches anything that still slips through |
| Validation | Invalid Mission Composer input | Inline form error, no job ever created (fails before entering the pipeline) |
| Permission | Unauthorized action attempt | 403 response, logged as `warning`, no state change |

### UI Error States (general pattern applied across all pages)
- Form-level validation errors: inline, field-adjacent, red text, does not clear other filled fields.
- Page-level load errors: retry button + human-readable message, never a raw stack trace.
- Partial-failure states (e.g., dashboard panel): isolated to the affected component, not a full-page failure.

## 23. Retry Workflow

Distinct from Mission-level "retry failed jobs" (§12.5, a human-triggered bulk action) — this section is the **automatic, system-driven** retry applied to individual job failures classified as transient (§22 table).

### Policy
- Max automatic attempts: **4** (matching the backoff pattern already validated in MK Connect's Gemini integration, Master Planning `01-research-mkconnect.md` §6, reused here for consistency of operational mental model).
- Backoff: exponential — base 20s, doubling per attempt (20s, 40s, 80s, 160s), consistent with MK Connect's proven `AI_CONFIG` retry approach.
- After max attempts exhausted → job moves to `dead_letter`, **not** silently dropped — this directly fixes the gap found in MK Connect's render/Veo workers, which have zero retry logic today (Master Planning `01-research-mkconnect.md` §3.6–3.7, listed as the top structural gap).
- Each attempt is individually logged (§20) with its specific error, so a `dead_letter` job's full failure history is inspectable, not just the final error.
- Non-transient categories (content policy, permission) never enter the automatic retry loop at all — retrying them wastes quota/credits on a guaranteed-identical failure.

### Manual Retry
Available from Job Monitor (§25) and Mission Detail: `Retry Manual` resets the attempt counter to 0 and re-enqueues at the job's original priority. Distinct from automatic retry in the log (`job.retried_manual` vs `job.retried_auto`) so analytics can distinguish systemic-issue patterns from one-off manual interventions.

## 24. Scheduler Workflow

The Scheduler is the component that decides *when* queued work runs — distinct from the Dispatcher (§25) which decides *what* runs next from the queue.

### Responsibilities
- Triggers the **Mission Dispatcher** tick (checks for queued Missions/jobs to dispatch) on a short interval (e.g., every 10s) — always-on background process, not request-driven, mirroring the architectural necessity already proven in MK Connect (render-worker/veo-worker as standalone polling loops, since generation duration exceeds serverless limits, `01-research-mkconnect.md` §1/§3.6).
- Triggers the **Higgsfield Status Poller** on its own interval (e.g., every 15s) to check in-flight job statuses.
- Triggers the **Reconciliation Job** hourly (§15.7).
- Triggers the **Dashboard Aggregator** every 5 minutes (feeds the pre-aggregated summary tables used by §8, satisfying NFR-6).
- Triggers the **Notification Digest** hourly (for the batched review-flag digest, §21).

### Resilience Requirement (NFR-2 / NFR-5)
Unlike MK Connect's single-worker render pipeline (a documented single point of failure, `01-research-mkconnect.md` §3.6), the Scheduler's triggered processes must be safe to run from **more than one worker instance concurrently** — every claim operation (a worker picking up a job) must be atomic (conditional `UPDATE ... WHERE status = 'queued'` pattern, the one part of MK Connect's design already proven correct and worth reusing verbatim, `01-research-mkconnect.md` §3.6). This allows horizontal scaling of workers without redesign later (NFR-2).

## 25. Mission Queue Workflow

The shared **Generation Job Queue** underlies all Missions — Missions do not have private queues.

### Dispatcher Logic
1. Query jobs in `queued` status, ordered by `priority DESC, enqueued_at ASC`.
2. Claim the next N jobs (N = available worker capacity) atomically.
3. For each claimed job: assemble prompt (Prompt Engine) → submit to Higgsfield (Integration Layer) → transition to `submitted`.
4. Paused Missions' jobs are excluded from the `queued` pool entirely (not dispatched, not counted against capacity) until unpaused.

### Page: Render Queue / Job Monitor (`/queue`)
- **Purpose**: Real-time visibility and manual control over individual Generation Jobs.
- **UI Layout**: Tabbed view by status (`Queued`, `Running`, `Retrying`, `Dead Letter`, `Completed` [recent only]) with counts in each tab label.
- **Components**: table (job ID, Mission name, subject, priority, attempt count, age, last error if any).
- **Buttons**:
  - `Retry Manual` (per-row, Dead Letter tab only) — see §23.
  - `Batalkan Job` (per-row, Queued/Retrying tabs) — **Click behavior**: sets job status `cancelled`, removed from active dispatch pool. **DB changes**: `generation_jobs.status='cancelled'`. **Logs**: `job.cancelled`. **Notifications**: none (routine operator action). **Failure recovery**: n/a (terminal, idempotent).
  - `Retry Semua yang Gagal karena Alasan Ini` (bulk, Dead Letter tab, filterable by error category) — Super Admin/Production Manager only, per Journey D in `01-dashboard-navigation-journey.md`.
- **Permissions**: view open to all with `mission.view_all`; retry/cancel require `mission.retry`/`mission.cancel`.
- **API Requirements**: `GET /api/queue?status=`, `POST /api/queue/:jobId/retry`, `POST /api/queue/:jobId/cancel`.
- **Database Tables**: `generation_jobs`.
- **Future Expansion**: per-worker capacity visualization, priority manual override on individual queued jobs.
